# v0.3.0 — Bring Your Own Key (BYOK) guide

| Audience | Tenant admins, integrators |
|---|---|
| Status | Shipped 2026-05-21 |
| Builds on | v0.2.0 customization foundation |
| Companion design plan | [`docs/plans/2026-05-21-v0.3.0-byok-design.md`](plans/2026-05-21-v0.3.0-byok-design.md) |

If your organization already has an Anthropic Enterprise contract, you
can wire OCR-to-Report to bill your account directly instead of the
platform's. Your Anthropic-side tooling sees one consolidated bill;
the platform's invoice (v0.4.0+) skips the BYOK-billed lines.

---

## 1. Mental model

```
                   ┌─────────────────────────────────────┐
                   │  tenant_provider_credentials        │
                   │  (per-tenant DEK encrypted)         │
                   └──────────────┬──────────────────────┘
                                  │ get_active_anthropic_credentials
                                  ▼
   POST /v1/transcripts ─►  AnthropicVisionAdapter.extract(
                              request,
                              override_api_key = unwrapped_plaintext
                            )
                                  │
                                  ▼
                       Anthropic billed against tenant's key
                                  │
                                  ▼
              usage_records.billing_path = 'byok'  ← v0.4.0 invoice skips
```

Three things flip when a tenant adds a BYOK key:

1. **Routing.** `AnthropicVisionAdapter` constructs a one-shot
   `AsyncAnthropic(api_key=<unwrapped>)` for that request only. The
   platform's shared client never sees the tenant's key.
2. **Billing.** `usage_records.billing_path = 'byok'` (a separate row
   from the tenant's `platform` row in the same period). v0.4.0
   invoicing sums only `billing_path = 'platform'` rows.
3. **Audit.** Each request emits `provider.byok_invoked` with the
   `credential_id` (never the key) so compliance teams can attribute
   a job to a specific key.

## 3. Wire shape

### `GET /v1/tenant/providers`

Returns every credential row for the calling tenant — active and
inactive (rotation history is retained for audit).

```http
GET /v1/tenant/providers HTTP/1.1
Authorization: Bearer sk_live_…
```

```json
{
  "providers": [
    {
      "provider": "anthropic",
      "active": true,
      "api_key_redacted": "sk-ant-…••••",
      "region": null,
      "rotated_at": null,
      "created_at": "2026-05-21T10:32:11Z",
      "updated_at": "2026-05-21T10:32:11Z"
    }
  ]
}
```

The plaintext key is **never** echoed back. `api_key_redacted` is a
fixed placeholder so the read path doesn't have to decrypt anything
on every poll.

### `PUT /v1/tenant/providers/{provider}`

Upserts the credential. Server validates the key against the
provider's API (Anthropic `/v1/models`) **before** persisting; a bad
key returns 400 with no row written.

```http
PUT /v1/tenant/providers/anthropic HTTP/1.1
Authorization: Bearer sk_live_…
Content-Type: application/json

{
  "api_key": "sk-ant-abc…XYZ1",
  "model_overrides": null,
  "region": null
}
```

```json
{
  "provider": "anthropic",
  "active": true,
  "api_key_redacted": "sk-ant-…XYZ1",
  "region": null,
  "rotated_at": null,
  "created_at": "2026-05-21T10:32:11Z",
  "updated_at": "2026-05-21T10:32:11Z"
}
```

The PUT response carries the **last-4 redaction** of the key you
uploaded, so you can confirm you pasted the right one. After this
response the redaction collapses to the placeholder.

A second PUT for the same provider rotates: the previous row goes
inactive with `rotated_at = now()`, a new active row is inserted in
the same transaction. Both `provider.byok_created` (first time) and
`provider.byok_rotated` (every subsequent PUT) appear in the audit log.

**Validation errors (400):**
- The provider rejected the key ("key validation failed").
- Transient network failure reaching the provider — retry.

**Other status codes:**
- `501` — PUT for `openai`, `google_vertex`, `tesseract` (shipped in v0.7.0).
- `400` / `422` — unknown provider id.

### `DELETE /v1/tenant/providers/{provider}`

Soft-disable. Returns 204 either way (idempotent). Future requests
fall back to the platform's key for the tenant. The credential row
stays in the audit history; `provider.byok_revoked` is recorded.

```http
DELETE /v1/tenant/providers/anthropic HTTP/1.1
Authorization: Bearer sk_live_…
```

## 4. SDK shortcuts

### TypeScript

```ts
import { Client } from "@ocr-to-report/sdk";

const client = new Client({
  baseUrl: "https://api.example.com",
  apiKey: "sk_live_…",
});

// List.
const { providers } = await client.providers.list();

// Set / rotate.
const status = await client.providers.upsert("anthropic", {
  api_key: "sk-ant-your-real-key",
});
console.log(`Key set: ${status.api_key_redacted}`);

// Revoke.
await client.providers.delete("anthropic");
```

### Python

```python
from ocr_to_report.sdk_py import Client
from ocr_to_report.sdk_py.models import ProviderUpsertRequest

client = Client(base_url="https://api.example.com", api_key="sk_live_…")

# List.
listed = client.providers.list()

# Set / rotate.
status = client.providers.upsert(
    "anthropic",
    ProviderUpsertRequest(api_key="sk-ant-your-real-key"),
)
print(f"Key set: {status.api_key_redacted}")

# Revoke.
client.providers.delete("anthropic")
```

`AsyncClient` exposes the same surface with `await`.

## 5. Using the web console

1. Open **Settings → Providers** (the sixth tab in v0.3.0).
2. Find the Anthropic row. The status badge shows the current state
   (`Platform` if you've never set a key; `BYOK active` once set).
3. Click **Add** (first time) or **Replace** (rotation). An inline
   password-typed input expands.
4. Paste your key and **Save**. The server validates against
   Anthropic's `/v1/models` before persisting; a rejected key surfaces
   inline as "Save failed" with the provider's reason.
5. To revoke: click **Revoke**. Confirm the destructive action.
   Routing falls back to the platform key on the next request.

The OpenAI / Vertex / Tesseract rows show **Coming in v0.7.0** —
that's the provider-expansion milestone.

## 6. Verifying it works

After setting a key, run a transcript:

```bash
curl -sS -X POST https://api.example.com/v1/transcripts \
  -H "Authorization: Bearer sk_live_…" \
  -F "file=@certificate.pdf" \
  -F "profile_id=pl.lo.swiadectwo_szkolne.v1" \
  -F "target_id=us-hs.v1"
```

Then look at usage:

```bash
curl -sS https://api.example.com/v1/usage \
  -H "Authorization: Bearer sk_live_…"
```

In v0.3.0 `GET /v1/usage` returns the platform row only (the v0.4.0
invoicing pass will surface both `billing_path` rows side-by-side).
You can confirm BYOK ran via the audit log:

```bash
curl -sS "https://api.example.com/v1/admin/tenants/<tid>/audit?limit=20" \
  -H "Authorization: Bearer sk_admin_…"
```

You should see `provider.byok_invoked` entries — one per job that
rode the BYOK path.

## 7. What this does *not* change

- **Model selection.** Your SLA tier still picks Haiku-first /
  Sonnet-fallback; BYOK only swaps the credentials behind that
  decision. The v0.3.0 plan deliberately split per-tenant model
  selection to v0.7.0 (provider expansion).
- **Caching.** The result cache is keyed on `(image_hash, provider,
  schema_version)`, not tenant. A BYOK tenant gets a free ride on
  prior cache hits across the platform; the platform never gets
  billed for a BYOK tenant's miss. This is correct: extraction is a
  pure function of `(image, schema)`.
- **Batch jobs.** Sync jobs and approve-from-park requests route
  through BYOK. The async batch path (Anthropic Batch API, ~50%
  cost) ships platform-billed only in v0.3.0; the explicit
  `billing_path='platform'` tag on the worker handler makes the
  intent visible. BYOK on the batch path is deferred to v0.7.0.

## 8. Operational notes

- **Key rotation.** A second PUT is the natural rotation. The old
  row stays inactive in the table for audit; `rotated_at` is set on
  it. The audit log carries `provider.byok_rotated` with the new
  `credential_id`.
- **DEK rotation safety.** If the tenant's master DEK rotates and an
  old ciphertext fails to decrypt, the request falls back to platform
  billing with a WARN log rather than 500. Manual remediation is to
  re-PUT the key (which encrypts with the current DEK).
- **Provider outages.** When the BYOK provider is unavailable, the
  request fails the same way a platform-billed request would —
  there's no automatic fallback to the platform's account. (That
  would defeat the billing intent.)
- **Logging.** The plaintext key is never logged. Audit entries
  redact to last-4. The PUT request body is excluded from any
  middleware-level access log.
